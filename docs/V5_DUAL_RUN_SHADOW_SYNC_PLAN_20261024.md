**B. stageを永続作成する際：**
1. stage12のDDLを原本への変更なしに限定し、予め定義した安全ゲート・復旧手段・操作範囲の承認後に実行。venuesを再作成・再コピーしない。stage schema/PK/index/default/sequence権限を検証。

3. コピー中のUPDATE/DELETEも取りこぼさないよう、**final consistency snapshot／完全主キー集合に基づくINSERT/UPDATE/DELETE差分の再照合**を実施。単純な最終日付カーソルは不十分。独立したstage採番シーケンスを維持。

## 深夜の短時間切替の現実的な境界（ユーザー指摘を反映）
- 既存の原本collectorが稼働中なら、直前オッズ・展示・気象が公式サイトから配信されている時点で引き続き収集・保存される。**移行準備中の収集停止は原則不要**。ただしサイト未掲載・定期ポーリング間隔・タイムアウトで取得できなかった瞬間値まで保証されるわけではない。
- 深夜03:30 JSTは通常のレース本番時間帯を避けられる良い候補。**GitHubで管理する`boat-v5-forward-window.timer`は`OnCalendar=*-*-* 07..23:0/5:00 Asia/Tokyo`（07:00〜23:55 JSTの5分間隔）なので、03:30には発火しない**。実ConoHaに設置されたunitがGitHubと一致するかだけ切替前にread-onlyで確認する。23:00 nightと01:20 catchupの完了、07:00 morningまでの再開、予期せぬ既存子worker/PG writerが動いていないことは別途自動チェック。
- **第1段階はV5の読み取り経路だけ切替（shadow、BUY OFF）**。旧原本writer/収集は止めず、`railway.public.v2_*`→`boat_data_stage.*`低負荷分割COPY＋完全主キー差分の追込を実施。03:30に原本とstageが同等・時刻鮮度PASSならV5の読取のみstageへ切替、遅延や異常があれば元の`boat_data.*`VIEW参照を維持/復帰。原本のVIEW13をDROP/置換しない。
- 第2段階の**収集writer本体の移転は別作業**であり、現在の13VIEW/live sourceの置換・自動停止を含む。全writerを認証して原本復元・自動切戻しが証明されるまで夜間にも実施しない。
- 後日補完が可能なのは主に確定結果等。収集中に取得済みのオッズ・展示・気象は`snapshot_at`とprovenanceを付けて移送し、**収集できていなかった瞬間の流動オッズ/初回観測は事後に完全再現できない**。前向きモデルROIに過去補完を混ぜない。
- **2026-10-25 03:30の自動ジョブは未予約**。未来の具体日・監査済スクリプト・fail-closed guardの承認が揃ったときだけ夜間無人実行を設定する。
