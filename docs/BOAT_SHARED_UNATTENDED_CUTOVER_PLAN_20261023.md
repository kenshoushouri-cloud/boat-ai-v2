## 方針
**実現可能。ただし現時点では自動切替の実行・予約は禁止。** 稼働中のConoHa PostgreSQL `railway` で、元データ13系列は`public.v2_*`物理実表・`boat_data.*`は同名の非更新VIEW。既存`deploy/conoha/boat_shared_bulk_stage_20261023.py --apply`/予約shellは宛先衝突で使用禁止。GitHub/ConoHaの`v5_data.venues`24件は研究/予備ステージであり稼働正本ではない。`boat_history_archive`約1GBは引き続き別DBのread-only原本、研究shadow/隔離展示は混合禁止。

目的は、**旧収集を動かしたまま、小さく複製し、短い収集静止時間に差分整合・全ルート切替**、異常時は収集を旧正本へ戻すこと。単に「深夜になったら停止する」ことではない。

## 実施順序：2フェーズ＋復旧

### 1. 事前のオンライン複製（昼夜、旧収集は稼働）
1. **writer/reader/timer/cron/backfill/修復/DDLを完全列挙**：朝/夜、5分毎forward、深夜公式結果catchup、手動補完、遅延処理と、再起動時旧表を作り直す処理まで。現状の`v5_active_writer_routes_readonly_20261022.py`は手掛かりの監査であり**全経路の完全証明ではない**。
2. 独立した**一時ステージschema/物理テーブル**に小さな表から複製し、13個の`boat_data.*`既存VIEWに直接`CREATE TABLE`しない。`v5_data`の旧案と現在の`boat_data`最終構成を混同しない。原表の列/制約/インデックス/デフォルト・シーケンス・権限・トリガー・外部キー・依存VIEW・raw/timestampの完全保持を確認。最初のpilotはvenues24件が候補。
3. 大容量（10/23実測ではrealtime odds651MB、展示135MB、天候188MB、結果艇別247MB等）は**テーブル単位・負荷制限・ディスク/WAL余裕チェック**。事前複製は静止点まで変化するため、INSERTだけでなく**UPSERTによるUPDATEやDELETEも検出できる差分追従**（確実な更新タイムスタンプ・CDC・再照合など）を事前実装。二重正本にしない。推測による日付のみの同期は不可。
4. **最新の外部/別媒体バックアップと限定復元試験**。10/19のみのバックアップは10/20以降の唯一の直前情報を保護しない。復元に必要な認証情報・設定・systemdユニット・ロールバック手順も別に保全。

### 2. 深夜の自動GO/NO-GO（専用の一回実行・原則NO-GO）
- 深夜が常に停止時間とは限らない。既知の夜23:00日次、01:20（加えて02:20/03:20等の可能性）catchupと、翌07:00の収集を**実際の`systemctl`/cron・プロセス・DBセッションで再確認**。時刻だけで終了と判定しない。
- 運用実施には**別途ユーザーの明示承認・対象表/予定窓の合意**が必要。条件を個別に機械検査する：
  - (A) 承認済みの13表別manifest・stage実表・全reader/writer/DDLルートの対応・切替後のレース収集が検証済み。
  - (B) 変更行を含む**最後の差分同期**、PKと重要列/件数/時刻の双方向整合、制約・index・権限・VIEW依存の整合がすべてPASS。
  - (C) 最新バックアップと限定復元試験がPASS。ディスク空き、WAL、DB負荷、タイムアウトが許容内。
  - (D) 当日直前情報の収集終了を確認。公式結果catchupなど**全writer+子process**を定めた短時間だけ静止。静止不可/遅延があればNO-GOで通常稼働継続。
  - (E) **全サービスの切替済みコード・設定のバージョン固定、戻し手順、非購入canary**が予めPASS。DB内の原子操作とsystemd設定変更は別物なので、混合writer期間を発生させない。
- GO条件が1件でも不明/不一致なら**一切切り替えない**。自動で旧writerを再開/維持し翌日へ延期、監査結果のみ記録。期限切れで切替強行しない。
- 全条件PASS後だけ、短い確認済み静止窓に**既存VIEW→正本テーブルの入替・全write/readルート統一**、単一正本による非購入収集canary、監視を実行。もし切替後の検査に失敗したら、旧正本へ安全に戻す手順を発動し、両方へ同時書込しない。戻せない失敗では勝手にwriter再起動せず管理者通知。

### 3. 移行後
旧実表は隔離し**すぐには削除しない**。数日以上の収集・read/realtime/historical/walk-forward照合、別媒体バックアップ再取得と復元、rollbackの実証後に、**1表ずつ別承認**して削除する。研究用shadow・隔離・archiveの扱いは別判断。予測とBUYは移行成功に連動して自動ONにしない。
