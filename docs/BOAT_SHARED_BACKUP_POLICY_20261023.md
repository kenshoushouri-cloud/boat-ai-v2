# ConoHa事前バックアップ＋移行後Google Drive定期自動バックアップ設計
更新：2026-10-23 JST。**方針案を確定・GitHub記録のみ。DB/Drive/サービスは未変更、バックアップ未作成、自動実行未設定。**

## 定期バックアップの正式対象と保存先の分離（ユーザー方針）
- **対象はV5の稼働・復元に必要な最小セット**：V5プログラム本体（GitHub原本のリビジョン＋ConoHa上の適用済みローカル差分）、systemd unit/timer・起動設定、必要なアプリ設定（資格情報は保護・暗号化して別管理）、モデル重み/前日学習状態、V5予測・精度評価・監査の復元に必要な記録、V5/V6共通原本の物理テーブル・索引/制約/DBロール復元手順、`boat_history_archive`のV5利用履歴。研究用でもV5再現に必要な唯一の原本は一覧検査前に除外しない。GitHub上のV5コードだけでは実行時設定・モデル状態は復元できない。
- **移行が終わるまでは**`boat_data`の13個は非更新VIEWであり、原本は旧`public.v2_*`物理表。`boat_data`VIEWだけをダンプしても大切なデータは守れない。正本の切替後にバックアップ対象を更新する。DB間参照・権限/拡張/DDL/タイムスタンプの復旧性も確認する。
- **V3/V4・旧実験環境は新しい定期ローテーションから除外**。ただし過去の復旧資産は別保存先に現状維持し、自動削除・上書きしない。V3/V4名のテーブルにV5の唯一の必要原本が残っていないかは除外前に依存監査する。共通データに混ざる不要なshadow/隔離表は原本保護方針を確認して別アーカイブへ。
- **保存先はGoogleドライブのV5専用側アカウント（B）を推奨**。10/23読み取りでV3/V4資産は主に別アカウントAの各旧世代フォルダ、Bには`boat-ai-v5-temp-202610`とV5鍵復旧用フォルダが存在していた。以前ConoHaで使用した接続名`v5_gdrive:`は履歴値であり、本番設定時に必ず接続先アカウント・権限・空き容量を確認する。Bの中に**新しいV5本番定期バックアップ専用フォルダ**を別途設ける案（名前・作成・接続は未実施）。10/19のV5一時ファイルや復旧鍵も移動/削除しない。
- **別Googleアカウントに分けることは保管整理・容量管理上有効**。ただし同一利用者の2アカウントは独立した災害対策の完全保証ではないため、復号鍵を独立保護し、定期的な別環境復元/将来外付けHDDへの追加保管も必要。新しい有料契約・容量追加は現時点で行わない。
- 対象変更・除外、バックアップ世代削除、自動バックアップ実運用の開始は復元試験と対象承認の後。**本項は構成方針のみで、今は定期実行未設定**。

## 段階と役割
1. **移行準備（GitHub・read-only）**：13系列の全writer/reader/DDL/cron、共有実表のstaging、差分同期（INSERT/UPDATE/DELETE）・全件照合、非購入canary、異常時切戻しをオフライン検証。Google Driveへの繰り返し全量転送はしない。旧10/19世代は絶対上書きしない。
2. **ConoHaローカル事前保全**：最初のDB変更を伴う複製/ステージ適用前に、現行の正本と必要設定を同一時点の復元可能なチェックポイントとして`/root/boat-v5-backups`など許可制のローカル領域へ一意の新ファイル名で作成。PostgreSQL `pg_dump -Fc`等の正式な方法、DB別の整合点、ファイル完了→SHA256→`pg_restore --list`→隔離環境で限定復元/読み取り試験。古いバックアップと現行原本は消さない。空きディスク、WAL、一時コピーとバックアップのピーク容量を先に検査。パスワードやage鍵はGitHub・ログ・チャットに記録しない。
3. **実物理切替直前の障害対策**：ConoHa内だけの保管は同一VPSの障害・ボリューム喪失・誤操作に無力。**少なくとも切替で唯一の原本を失わないための最新・独立した復元手段**を別媒体へ用意し（必要に応じて変更分を含む新世代暗号化バックアップを一度だけDriveへ転送）、限定復元が合格しなければ夜間切替はNO-GO。ローカルdumpだけで「災害対応バックアップ済み」と判定しない。外部保全の実施時点・対象容量・リスクは切替直前に再査定し、無断転送/契約変更をしない。
4. **事前コピー＋深夜条件付き切替**：小さな表から旧writerを動かしたまま別stagingへ複製、変更分を追従。合意済み静止窓に全子ジョブ/cron/DB writer停止確認、最終差分・PKと内容・VIEW依存・ロールバック試験・非購入canaryが全部合格したときだけ正本切替。不合格なら旧表の収集を維持する。既存`boat_data.*`13個の非更新VIEWへ直接INSERT不可、VIEWと衝突する旧一括スクリプトは実行禁止。
5. **整理済みの最終保全**：切替・安定動作とデータ照合が確認できてから、共通物理DB`railway`と別履歴DB`boat_history_archive`・必要設定の新しい世代の暗号化バックアップをGoogle Driveへ保存する。旧バックアップは独立したリカバリ世代として残し、名前/ハッシュ/復元済み世代を確認するまで削除・上書きしない。

## 整理完了後の自動運用案（提案・未有効）
- **毎日1回、結果補完終了の確認後・朝07:00収集前**にバックアップを試行。01:20/02:20/03:20等catchupや23:00日次・forwardと重なっていれば**その回はスキップ**、翌日実行・異常通知。時刻固定だけで「収集終了」と判断しない。DBスナップショットはトランザクションで一貫性を確保する。別DB間の共通時点は当然には保証できないので記録する。
- `pg_dump`等の標準ツールでDBごとに整合バックアップ→暗号化（例：`age`）→一意の世代名で`rclone copy`→サイズ/ハッシュ等の照合・`pg_restore`目録の検査・バックアップ成功記録。**復元試験は別の隔離先で定期実施**（まず設定時、その後少なくとも月次等）。単なる`rclone copy`成功だけで復元性PASSとしない。
- 初期提案：**日次7世代＋週次4世代**（容量実測とGoogle Drive利用可能残量に基づき調整）。古いV3/V4・10/18〜19世代はこのローテーションの削除対象外。過去実測の10/19メイン暗号化ファイル約298MB＋履歴約52MB=**計約350MB/世代**だが、2026-10-23以降の実容量・成長を保証しない。独立Drive2アカウントの容量/利用権限・世代復元を検証してから稼働。
- 低負荷運用：CPU/IO nice・排他lock・時間上限・容量/WAL事前検査・同時実行防止・暗号化済みファイルのみクラウド送信。途中失敗は未完成を`complete`にしない。**前回成功世代を維持**し、失敗が続けば本人が気付ける通知を出す。Driveトークン・rclone config・秘密鍵・パスフレーズは非表示。
- 差分バックアップやWALアーカイブは設計・継続再生試験なしで採用しない。初期はフルの暗号化世代が分かりやすく復元可能。ただし2GB ConoHaの負荷/保管容量で日次不可なら、対象/頻度を実測で調整し、次善策の復元試験を行う。
- **本番導入の明示承認が別途必要**：Google Driveの定期転送・保持期限・通知先・復元頻度・システムdタイマー/cron有効化。現時点では設計のみで自動タスクやConoHaスケジュールは作成していない。

## 安全ゲート
- バックアップを作る前のバックアップ検査は必要最小限とし、**移行準備の開発を先に進める**。
- ローカルのみのバックアップは短時間の操作失敗からの復旧用であり、オフサイトと同一視しない。
- 既存Drive 8件の内容/復号/独立復元は未認証。10/19以降に増えた展示・オッズ・結果の保護を旧世代だけで満たしたと扱わない。
- 移行と定期バックアップのどちらの作業も、V5実予測、真の収益検証、自動購入の稼働を自動解除しない。
